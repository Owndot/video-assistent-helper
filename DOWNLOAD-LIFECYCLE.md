# Download lifecycle (Helper issue #6)

Scope: safe completion/cancellation and disposal of interrupted private downloads. This is not automatic persistent download recovery. No browser protocol, authentication, media player, signing policy or APK change is part of this work.

## Responsibilities and guarantees

| Path | Network/status owner | Temporary data / publication | Resume after interruption |
| --- | --- | --- | --- |
| Uncredentialed native file | Android DownloadManager (DM) | Android owns its destination and notification. The Helper watches for up to 25 seconds; that in-memory status is not a durable DM history. | Android manages it, independently of the Helper service. Helper does not reconstruct its watcher after process death. |
| Cookie/referrer-bearing native file | `Fetcher.Http.streamToFile`, `Downloads` task, foreground Helper service | Fixed 64 KiB network buffer; private `cache/dl<ID>` work; then controlled publication | At most four attempts in the same worker. A trusted validator and matching 206 range permit appending. A changed validator or an ignored Range/200 response causes a fresh replacement, never mixed bytes. |
| Browser proxy file | Browser/GM fetches, `/pull` leases, file-backed authenticated `/push`, `Downloads` task | Existing bounded windows and file spools, then the same publication path | No durable browser/job recovery. Explicit cancellation interrupts the owning worker, which closes that job's proxy; late uploads are rejected. Closing a tab alone need not notify the Helper: its existing finite request lease (10 minutes) bounds this wait. |
| HLS / DASH | Existing cores and bounded workers; native or proxy transport | Private parts and mux result; same publication path | Existing bounded per-part retries only while the job lives. No crash-resume journal. Android mux execution is not covered by the new host models. |

A task goes from `startet` through progress (and optionally `zusammensetzen`) to one of `fertig`, `abgebrochen`, or `Fehler: …`. Only successful file publication commits `fertig`. Cancellation and the Helper's final commit use a short per-task metadata lock. Provider updates and filesystem moves occur **outside** this lock. The Helper commit point is the checked terminal-state transition **after** the provider/move returns: a cancellation recorded before that transition wins and rolls the row/file back, without `fertig`; a cancellation after it is a no-op. A provider can expose a complete file just before returning: public Android APIs offer no transaction spanning Binder and our task state, so transient visibility before a cancelled attempt is rolled back is possible. A hard kill during that interval also cannot guarantee durable cancellation; completed non-pending files are conservatively preserved on restart. Errors displaying a notification cannot retroactively invalidate a successfully committed file. Other tasks have independent cancellation, streams and output paths.

Service shutdown sets an admission stop and snapshots active IDs under a short admission lock, then signals those tasks outside that lock. `cancelJob()` only changes task metadata and interrupts its worker; it performs no provider, file or proxy cleanup on the main thread. Workers close proxies/remove spools in `finally`. No new cancellation thread, executor, timer or queue is added. Admission filesystem/ID-sync work is outside the admission lock; an in-flight admission from a previous service generation cannot register after stop/restart. Queued/running tasks from the stopped generation remain cancelled even if the same-process service restarts. Progress/error/cancel terminal states are protected against late rewrites. The short task lock also covers worker registration, the interrupt signal and unregistration: an already captured cancellation cannot hit a pooled thread after it has moved on to another job. A controlled signal-gate regression reproduces this reuse race in the earlier implementation and checks that the next task inherits no stale interrupt. Android framework server/brightness shutdown behavior is otherwise unchanged. Android DM jobs remain OS-owned. No global network or playback cancellation is introduced. Service shutdown is cooperative; a blocked `HttpURLConnection` read is not guaranteed to unblock on `Thread.interrupt()`. The existing 15-second connect and 30-second read timeouts remain the native bounds per network operation. HLS mux and provider I/O can also delay cooperative cleanup; no immediate Android/OEM timing guarantee is claimed.

## Proven defects and corrections

The exact baseline is merge `044784068b4b74621f0b45dbbf203780d17ebefe`.

* An output-stream error left an inserted MediaStore `IS_PENDING=1` row. Write, flush/close, null-stream and zero-row publication failures now roll the row back. The pending flag is cleared only after the whole copy closes successfully and cancellation is checked. A provider failure preventing deletion is still an error and cannot be guaranteed away by Java cleanup.
* Cancelling during the save copy could still publish the file and report `fertig`. Task cancellation is checked through copying and immediately before publication, serialized with the commit. Both pending and private work are discarded on ordinary failure/cancellation.
* On API 26–28 saving directly into an existing same-name destination overwrote it and exposed partial bytes. A same-directory `.evp-pending-*.part` file is now copied, closed and synced before a no-replacement move; colliding names get a suffix. Failed staging is removed. The directory belongs to the app; no claim is made about arbitrary external writers racing on an unreliable filesystem or power-loss atomicity.
* The native credentialed reader could treat the declared length reached before a read failure as successful completion on the next attempt. It now requires a successfully validated end/close, retries from zero if a failed attempt already reached that length, and deletes its output after final error. This path now also uses the existing strict response-framing validation; contradictory TE/CL and invalid resumed range metadata are permanent errors, without retries.

The new SDK-only check also exposed a pre-existing compile failure: `OsConstants.O_DIRECTORY` is not a public Android SDK symbol. The ID-journal directory sync now uses public `Os.open(O_RDONLY)`, `Os.fstat`/`S_ISDIR`, and `Os.fsync`, preserving descriptor type checking and sync before an ID is returned. The durable ID format and protocol are unchanged.

For known HTTP lengths/ranges, completion requires the exact validated size. Unknown-size responses require a clean stream end; without a trusted length or independent digest no implementation can detect a server intentionally ending an otherwise valid unknown-length representation early. Content is not published before the transport/core and save checks finish.

## Hard process death and next start

A hard kill runs no Java `finally`/`onDestroy`. In-memory status, cancellation and resumable-prefix metadata disappear. No new process reuses or appends an old partial download. Durable reserved job IDs remain unchanged.

Before starting the local server, once per process, the Helper discards:

* its private `cache/dl<signed-number>` directories;
* its private external `Video-Assistent/.evp-pending-*.part` staging files;
* only proved direct Helper MediaStore rows with `IS_PENDING=1`, the current owner package, exact `Download/Video-Assistent` folder (with/without trailing slash), and no DownloadManager `DOWNLOAD_URI`.

Direct publication first creates and syncs a tiny private `files/download-pending-v1/evp-publish-<random>.pending` ownership marker, then prefixes the requested filename with that private token and `--` for the MediaStore pending `DISPLAY_NAME`. The proof matches the unchanged safe token prefix, tolerating provider normalization of trailing extensions/collision suffixes. The final update sets the requested real name and clears `IS_PENDING`. This marker is an ownership intent, with no media bytes, key, progress or resume metadata. Creating it before insert covers a process kill between insert and receiving its URI. It is removed after successful publication or confirmed rollback. Uncertain insert/cleanup failures retain it for the next process start.

Recovery explicitly calls public `MediaStore.setIncludePending()` (API 29+) because Q collection queries otherwise add `is_pending=0`. It intersects the scoped pending query with existing private marker token prefixes, rejects any `DOWNLOAD_URI`, and repeats ownership/pending/folder/name/source checks in the targeted delete. Completed, foreign, DM and **unproved** historical pending rows are preserved, even at the same package/folder. Unknown old rows are deliberately not guessed to be ours. Provider query exceptions/null cursors and unsuccessful deletion abort recovery, preserve evidence and leave initialization retryable. A successful pass removes stale proofs whose rows are gone or completed; repeating it is safe.

API/source check: Android Q's public [setIncludePending](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-10.0.0_r47/core/java/android/provider/MediaStore.java) appends `includePending=1`; its [Downloads provider query](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/android-10.0.0_r47/src/com/android/providers/media/MediaProvider.java) otherwise appends `IS_PENDING=0`. The [modern provider](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/a183e2b92c71d86ec7b104c116ef3f4dbcbb523f/src/com/android/providers/media/MediaProvider.java) explicitly honors legacy `MediaStore.getIncludePending(uri)` as `MATCH_INCLUDE` even though the public URI helper is deprecated since API 30. This is source/API evidence, not an OEM execution claim.

Published rows, foreign owners, other folders and completed legacy files are preserved. A regular service restart in the **same** process does not repeat recovery over workers still unwinding. Cleanup failure aborts startup/download admission instead of pretending recovery succeeded. This does not immediately remove residue while the process is dead, reconstruct progress, guarantee filesystem durability on power loss, or provide automatic resume after force-stop/reboot. A process can die just after a complete file is published and before its notification; that complete file is retained.

## Targeted evidence and limits

`bash tests/java/run_download_lifecycle.sh` runs actual production `Downloads`, `Fetcher` and actual `HelferService.onStartCommand/onDestroy` callbacks with explicit host models of Android APIs. The models enforce the default collection pending filter, fault output writes/closes/updates/query/delete and block provider commits before/after their side effects and implement a persistent, scoped provider model; they do **not** execute Android MediaProvider, DownloadManager, notification delivery, foreground-service scheduling, mux, or directory fsync.

`bash tests/java/run_download_lifecycle.sh --transport` additionally runs:

* real local HTTP parsing of conflicting/valid framing;
* stalled read/timeout cancellation, bounded retries and a simultaneous healthy download (test-only 150 ms read timeout; connection opens are snapshotted atomically at the cancellation event, so legitimate earlier timeout retries do not masquerade as retries after cancellation; not a production timeout change);
* existing 64 MiB native downloads at `-Xmx32m`, exact SHA-256 bytes, valid Range/If-Range resume, ignored ranges, unknown lengths, invalid ranges and cancellation;
* a separate JVM killed forcibly **during an actual save**, leaving real private work and a partial pending provider-model file, followed by another JVM's actual startup recovery. Kept complete/foreign/unrelated bytes and refusal to resurrect state are asserted. This is a true host process kill, not a Java exception, and **not** an Android process-kill proof. Legacy crash staging cleanup is seeded, not a real Android 8/9 kill experiment.

The branch-only counterproof script checks the four original independent failures and the three reviewed P2 failures against unchanged baseline production classes. Permanent CI runs the corrected lifecycle tests for ordinary PRs and `main` pushes. The existing memory job retains native/proxy 32 MiB heap, HLS/AES/DASH, HTTP framing/range/validator, timeout, late-upload, restart-ID and authentication regressions. The reviewed `6a86fdd` tree independently fails the new pending-recovery, actual-service-main-callback and deterministic first-legacy-save counterexamples. The fixed tests also check a blocked A commit does not prevent B cancellation/stop/restart, repeated/late cancel, stale admission generations, completed/foreign/same-package DM/unproved preservation, and provider-error retries. The legacy race test runs both real `save()` calls with JDK-17/21-only filesystem-check interposition (`SecurityManager`, isolated test JVM with `-Djava.security.manager=allow`), making a concurrent mkdir observable at the exact branch; it changes no product security rule. It checks distinct same-name outputs, byte integrity, permission denial, invalid directories and staging cleanup. CI pins JDK 17; this test mechanism must be replaced before moving that job to JDK 24+.

A compile-only check uses the hosted Android SDK for actual `Downloads`, `HelferService` and `Keys`; it builds no APK and does not execute the service.

Issue #6 remains **open** pending independent review and actual Android provider/service/force-stop/reboot validation. In particular API 26–28 external storage and API 29+ owned pending-row queries/deletion, Samsung/OEM service timing and real browser-process termination are **not verified on real hardware**. No manual Samsung checklist is required by this change. A larger persistent crash-recovery mechanism is deliberately deferred; discarding owned unfinished work is the smaller safety guarantee.
